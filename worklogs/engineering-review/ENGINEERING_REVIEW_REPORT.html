§1Executive status

Round 9 changed no code. The reported per-slot Level-Match contamination has a real mechanism — abMatchGain[] is never reset on any restore path and never serialized — but its reported impact does not occur: the first A/B switch after a no-A/B restore does not move the output level. Three independent measurements say so, including the one configuration that could have flipped it.

ER-STATE-13 · REFUTED on impact

The review's own rule requires stale state and an output-level change. The stale state is real; the level change is not. Matched same-instance counterfactual, fresh-instance control, and a worst-case switch with no settle at all — all indistinguishable.

The decisive test exists because of round 8

With both slots now holding the restored state, an A→B switch applies identical parameters, so the injected match gain is the only variable. And A→B→A decontaminates the array by construction, giving a clean control on the same instance with the same loudness history.

Why it is inert

The injection lands at the silent bottom of the switch duck, where output is muted, and setParameters re-targets from the live loudness.getMatchGainDb() every block. Level Match is a continuously re-derived measurement, not stored state — so overwriting it briefly reaches nothing. Residual: a readout excursion (−7.10 → −2.18 dB) converging in ≈65–85 ms.

Two probe defects, caught before trusting the numbers

v1 read the gain before processBlock had consumed the injection and declared it absent. v2 measured RMS in a window containing the 34 ms switch duck and reported a −2.60 dB "level change" that was the fade. Both are this programme's recurring vacuity class.

Round 8 confirmed and fixed one real defect: a session carrying no A/B data left the previous project's A and B sounds loaded. A host reuses one plug-in instance across projects, and two restore paths — a v0.2 session, and any AnamorphRoot whose AB child is absent — never reset the slots, so the session's own sound loaded correctly and then pressing A or B recalled a sound from the project before it. Reproduced before anything was changed, fixed in six lines, and pinned by a five-leg regression test that fails 8 checks without the fix.

ER-STATE-12 · CONFIRMED → FIXED

Measured, not argued: after a v0.2 restore, switching to B played the previous project's B (raw width 0.10 against a restored 0.75); with the previous project left active on B, the first switch read its A (0.90) and its active index survived as well. Both slots, and the index.

The fresh-instance leg refuted its own premise

Written expecting a vacuous pass — the slots "start invalid" — and it failed at 0.5. The constructor seeds both slots EAGERLY, so by the time a restore arrives they are already valid, holding the open/Default state. A fresh instance was affected too. The comment was corrected; the measurement stood.

Semantics taken from the registry, not the code

SERIALIZATION_REGISTRY.md already gives active a default of 0 and the slot params "lazily initialised from current", and states the rule outright. So: deterministic reseed — not clear, not migrate. No schema change, no architecture gate, and a blob that carries an AB node restores exactly as before (leg 5 pins that direction).

ER-RT-05 · DOCUMENTED, nothing changed

All four documents already describe the lint's same-file closure in terms that cannot be read as whole-program coverage. The census was re-measured rather than assumed: 83 matches across 12 files, identical to round 3, every cross-file-reachable DSP match still inside that module's prepare().

R3 · KI-028 closed (mostly)

An abandoned value-box press really does block undo. R3 · the guard was in the wrong place

Round 2's non-finite check ran on the CONVERTED value, and conversion clamps — so an infinity arrived already laundered into a finite range endpoint. Measured: "inf" pinned Width to its maximum, "abc" to its minimum, on both restore paths. The test now runs on the input, in one shared predicate.

R3 · repairs did not reach the file

A corrupt value was repaired in the live parameter and then written straight back out: the saved blob still read value="nan". Invisible here, because raw is preferred on reload — but the file stayed damaged for anything else that reads it.

R3 · three vacuous probes

A forced duck is dry-filled, so a level probe cannot see it. A 1 kHz tone through a 12 ms Haas delay is exactly 12 periods, so side energy is identically zero. And a leak probe with no positive control cannot fail. All three printed a clean pass over nothing before being rewritten.

§6Decisions needed from the maintainer

D-1 — KI-027: move latency-notification delivery off the audio thread APPROVED & IMPLEMENTED r4

Defect (unchanged, re-verified): automation of Drive/Algorithm delivers the APVTS callback on the audio thread; when reported latency actually changes, the JUCE chain takes locks, allocates and write()s inside processBlock.

Round 2 narrows it. Oversampling is not a host parameter — it lives in InternalState and defaults to Off — so at factory defaults reported latency is identically 0 and the expensive branch is unreachable until a user selects 2x/4x/8x in Settings. The rate is bounded at one dispatch per parameter per block. The priority inversion is mitigated by PTHREAD_PRIO_INHERIT on Linux/macOS, but not on Windows.

Two candidates are refuted. The editor's 24 Hz poll is the only message-thread tick in src/ and does not exist with the editor closed — a closed-editor render would never learn the new latency, which is worse than the defect. An AsyncUpdater reproduces the same postMessage (lock + possible reallocation + write()) on the audio thread.

What you are approving: keep the synchronous call when MessageManager::existsAndIsCurrentThread(), otherwise set one relaxed atomic flag consumed by a processor-owned ~20 Hz juce::Timer. Cost: the host learns a latency change up to one tick later. Gate: threading model + latency delivery.

D-2 — RISK-007: guard off-main-thread state calls, or accept as documented? DEFERRED r4 — no code change

The measurement asked for in round 1 is done. AnamorphStateTests --state-thread-probe under ThreadSanitizer reports four data races: abActive (written by setStateInformation, read by canUndo()), the abUndo vector's internals twice, and a juce::String refcount exchange against a String copy. So if a host makes these calls off the main thread while an editor is open, this is undefined behaviour — not a theoretical concern.

What remains is only the host question: VST3 annotates both calls [UI-thread] and JUCE hosts lock around them, so the exposure is the macOS AU autosave path. Options unchanged: (a) accept and keep documented; (b) a narrow mutex over the state-set members; (c) callAsync marshalling of the metadata tail. (b) and (c) are threading-model changes.

D-4 — malformed-value recovery and repair serialization APPROVED r4

The round-3 P2/P3/P4 fixes change what a MALFORMED serialized value restores to (a range endpoint → the parameter default) and make a repaired value reach the saved state. The brief requires ARCHITECTURE_REVIEW_GATE approval before merge for any change affecting malformed-value recovery, legacy migration, or saved-state compatibility, so they are implemented on the branch and flagged rather than treated as ordinary fixes.

What does NOT change: no schema field added, removed or renamed; no well-formed file loads differently; the serialized shape is untouched. SERIALIZATION_REGISTRY.md already specifies "per-parameter defaults" for the ABSENT case — this makes the MALFORMED case agree with it instead of silently choosing an endpoint.

Deferred by the maintainer, 2026-09-01. No mutex, no callAsync, no state-architecture change; exposure is host-determined and that is what the deferral turns on. The measured TSan findings stand and remain valid: the abActive race, the abUndo vector races and the juce::String refcount race.

D-3 — Level-5 audition for v0.9.6 PASSED · COMPLETE

Performed by the maintainer against the final v0.9.6 build; PASSED. Precondition 7 discharged, recorded 2026-09-01. Round 5 had written the twelve-item protocol and record format in docs/procedures/LEVEL5_AUDITION.md; the audition itself was the maintainer's, as a human sign-off requires. Seven record fields were not supplied and are marked NOT RECORDED rather than inferred from the protocol.

The 2026-08-15 audition covered v0.9.4; since then the x86-64 machine code changed everywhere (ADR-0031/0032) and 0.9.6 changed audible behaviour in the defective windows. A DAW session by a human is required; nothing in CI can stand in for it (TESTING_POLICY Level 5). Until then HANDOVER lists the tag as blocked by three human items (licence, checklist, audition).
