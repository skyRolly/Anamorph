§1Executive status

Round 2 recovered CI, fixed three confirmed defects — two of which made the plug-in inaudible or wrong in ordinary use — measured RISK-007 rather than reasoning about it, and corrected decision D-1 by refuting two of its own candidate fixes. Round 1's sweep (eight adversarially-verified lenses, 17 findings confirmed, 2 refuted, ~75 areas ruled out) remains the baseline below. The headline results:

R2 · worst defect found

Every activation ducked. The engine was prepared before it was told the current settings, so its first look at them read as a settings change and got the click-free mute. Measured at 0.4 % of level for ~35 ms on every insert and every project load. Fixed; State test 16.

R2 · worst latent defect

A corrupt value silenced the plug-in permanently. value="nan" in a session or preset was adopted, output peak measured 0.000000, and saving wrote it back out. Fixed at both ingress points; State test 17.

R2 · RISK-007 measured

The TSan probe reports four real data races on exactly the members round 1 predicted. The code half of D-2 is settled; only the host question remains.

R2 · D-1 corrected

Two of D-1's candidate fixes are refuted: the editor poll does not exist with the editor closed, and an AsyncUpdater reproduces the same syscall. Reachability is also lower than filed.

§6Decisions needed from the maintainer

D-1 — KI-027: move latency-notification delivery off the audio thread? REVISED r2

Defect (unchanged, re-verified): automation of Drive/Algorithm delivers the APVTS callback on the audio thread; when reported latency actually changes, the JUCE chain takes locks, allocates and write()s inside processBlock.

Round 2 narrows it. Oversampling is not a host parameter — it lives in InternalState and defaults to Off — so at factory defaults reported latency is identically 0 and the expensive branch is unreachable until a user selects 2x/4x/8x in Settings. The rate is bounded at one dispatch per parameter per block. The priority inversion is mitigated by PTHREAD_PRIO_INHERIT on Linux/macOS, but not on Windows.

Two candidates are refuted. The editor's 24 Hz poll is the only message-thread tick in src/ and does not exist with the editor closed — a closed-editor render would never learn the new latency, which is worse than the defect. An AsyncUpdater reproduces the same postMessage (lock + possible reallocation + write()) on the audio thread.

What you are approving: keep the synchronous call when MessageManager::existsAndIsCurrentThread(), otherwise set one relaxed atomic flag consumed by a processor-owned ~20 Hz juce::Timer. Cost: the host learns a latency change up to one tick later. Gate: threading model + latency delivery.

D-2 — RISK-007: guard off-main-thread state calls, or accept as documented? EVIDENCE COMPLETE

The measurement asked for in round 1 is done. AnamorphStateTests --state-thread-probe under ThreadSanitizer reports four data races: abActive (written by setStateInformation, read by canUndo()), the abUndo vector's internals twice, and a juce::String refcount exchange against a String copy. So if a host makes these calls off the main thread while an editor is open, this is undefined behaviour — not a theoretical concern.

What remains is only the host question: VST3 annotates both calls [UI-thread] and JUCE hosts lock around them, so the exposure is the macOS AU autosave path. Options unchanged: (a) accept and keep documented; (b) a narrow mutex over the state-set members; (c) callAsync marshalling of the metadata tail. (b) and (c) are threading-model changes.

D-3 — Level-5 audition for v0.9.6

RELEASE_POLICY precondition 7 is per-version. The 2026-08-15 audition covered v0.9.4; since then the x86-64 machine code changed everywhere (ADR-0031/0032) and 0.9.6 changed audible behaviour in the defective windows. A DAW session by a human is required; nothing in CI can stand in for it (TESTING_POLICY Level 5). Until then HANDOVER lists the tag as blocked by three human items (licence, checklist, audition).

D-4 — Version handling of this round

The round shipped as v0.9.6 (dated CHANGELOG section, renumbered first-tag references) per the repository's established pattern — every user-visible change set gets a version and no tag has ever been cut. Override if you want it folded differently; the 0.9.5 section's dated record was left untouched either way.
