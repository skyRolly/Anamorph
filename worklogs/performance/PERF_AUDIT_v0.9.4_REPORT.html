Anamorph Engine Cost Audit

Six optimization waves have already run. This round measured what is left, and found one dominant cost that the previous rounds closed as absent — because they measured it in the one configuration where it is switched off. That fix has since shipped in v0.9.5, and the product tree reproduced every predicted figure to one decimal place.

Method: callgrind instruction attribution + committed AnamorphBench Machine: Intel Xeon @ 2.80 GHz, 4 cores, gcc 13.3.0 Worklog: worklogs/performance/PERF_AUDIT_v0.9.4_INVESTIGATION.md

Executive summary

The engine is in good shape. The transparent idle floor costs 455 instructions per sample and a fully-engaged working configuration costs 1,749 — roughly 1 % of one core per instance at 48 kHz on the machine named above. Waves 1–6 did their job: every obvious gate is in place, and the two largest remaining consumers are structures those waves already halved.

One finding changes the picture. VelvetNoise carries 20,369 instructions of fixed per-block cost — 84 % of the engine's entire per-block overhead — and it scales with sample rate while being divided by block length. At 192 kHz with 32-sample buffers it is 62 % of the whole engine. A bit-exact fix was implemented in a throwaway build, verified across 144 configurations, and measured.

Bottleneck analysis

A closed question, reopened

Wave 5 attributed small-buffer per-block cost and closed it: “+13–20 %… ~4.5k Ir of fixed work per block… no single dominant item”. That closure was carried into the roadmap.

Solving cost(b) = A·48000 + B·(48000/b) from the 32- and 256-sample runs gives two very different answers depending on what the plug-in is set to:

ConfigurationFixed per blockMarginal per sample
transparent defaults3,581 Ir464.9 Ir
working — the algorithm actually engaged24,287 Ir1,558.6 Ir

Wave 5's figure reproduces exactly — for the transparent default. In the configuration a paying user runs it is 6.8× larger, and 20,369 Ir of it (84 %) is VelvetNoise::processBlock alone: very much a single dominant item.

The reason the earlier closure missed it is mechanical, not careless. The H5 tap-outer gather is gated on currentAmount > 0.0f || targetAmount > 0.0f (src/dsp/VelvetNoise.cpp:132-135), and the default algoAmount is 0. Measuring per-block cost at the transparent default measures the one configuration in which the dominant per-block item is switched off.

The mechanism

The H5 fast path rebuilds its linear history image from the ring on every block:

// src/dsp/VelvetNoise.cpp:139-140
for (int j = 0; j < decorrSamps; ++j)
    linHist[(size_t) j] = midHist[(size_t) ((writePos - decorrSamps + j) & histMask)];

decorrSamps = round(0.045 × sr) — 2,160 samples at 48 kHz, 8,640 at 192 kHz — and the loop does not depend on numSamples. Measured at ≈ 9.4 Ir per history sample, it therefore grows with the sample rate and is divided by the block length.

Solved per configuration, the fixed term is 20,369 Ir/block at 48 kHz and 78,690 at 192 kHz — 3.86× for a 4× rate, as the mechanism predicts — while the marginal term is 118.8 Ir/sample at both. That invariance is the signature of a cost that belongs entirely to the per-block refill.

H5 is still the right structure: it turned 64 random ring reads per sample into unit-stride runs, and that win is real at 128 samples and above. What it also introduced is a per-block term that overtakes the win as the buffer shrinks and the rate rises.

Bypass costs marginally more than processing

A host-bypassed instance measured 85.1M Ir/s against the working reference's 84.0M. The whole chain still runs and the bypass ring read-back is added on top.

This is not an oversight. src/dsp/AnamorphEngine.cpp:790-796 states the contract: the processing and the Level-Match analysis always run, so Measure and Predict keep working while bypassed. loudness.process() is handed the processed signal (:1137), so the chain cannot be skipped without freezing the Measure readout — the exact live contract that W3-7 was rejected for breaking. And pid::bypass is registered as the host bypass parameter, so it applies to every bypassed instance in a session.

Three limits on the GUI numbers

These come from the Linux software renderer; macOS (CoreGraphics) and Windows (Direct2D) rasterize differently, so the absolute figures do not transfer. paintEntireComponent forces a full repaint — the resize case, not the steady state. And the juce::Timer / VBlankAttachment tick path, where the Wave 1–4 idle gates live, needs a message loop and was not measured: the “idle GUI cost ≈ 0” claim is neither confirmed nor challenged by this round.

RISK-002: no dropout-class transient found

The multiband split drag costs +11.2 % over the static 4-band state, of which __tan_fma is 3.26 % — the per-sample coefficient recompute Wave 3 already cut from 12 tan/sample to 3. Nothing in either instrument suggests a cliff.

This does not close RISK-002. Closing it needs the wall-clock instance count on a named, held-still machine — which is item 01 of the roadmap.

A7-1 — why it is the whole recommendation

The retained tail of linHist is, by construction, the previous block's linHist shifted left by that block's length: the ring is written with exactly the mids the image already holds. So the decorrSamps-long masked ring walk can be a memmove of the same floats, guarded by a validity flag that the non-fast paths and reset() clear.

It was implemented in a throwaway build and measured, because a bit-exactness claim has to be earned:

What the product tree measured v0.9.5

The shipped implementation is not the throwaway one: it clears the slide offset on entry to processBlock rather than from an RAII guard on each non-gather exit, so every other path — and every path a later round adds — leaves the image invalid by construction. The numbers came out the same anyway.

Cost: about 20 lines in one file, two new members, one invalidation point in reset(). It touches no parameter ID, no serialization schema, no thread model, no signal order and no reported latency — no hard-stop class.

The strongest case against, stated because it is real

It adds a cross-block cache-validity invariant to a module whose fast path already carries a five-clause eligibility gate. A future edit that takes the fast path without maintaining the flag would read a stale history — silently, and only in the first block after the mistake. Mitigation: clear the flag from a scope guard on every non-fast-path exit rather than by hand at each return, and add a regression test asserting bit-equality between a run at block 32 and the same audio at block 256.

Why the biggest number is not the recommendation

Multiband is 41.7 % of the working reference and the obvious target. It is not proposed, for reasons already on the record:

  • Wave 2 (H6) replaced JUCE's filter with a flat-state clone; Wave 3 cut the glide from 12 tan/sample to 3 and halved the allpass compensation.
  • What is left is a serial TPT recurrence — s1→s2→s3→s4 per sample — which cannot be vectorized across samples at all.
  • Vectorizing across banks is the W5-D shape, already prototyped at 1.10× under the frozen SSE2 flags. The real win needs -march=haswell+ — a numerics-frozen build-contract change that would itself introduce FMA and break the bit-exactness the prototype relies on.
  • The roadmap already files LR4 SIMD as “Defer … only worth opening alongside the AVX2 decision.”

Proposing it again without an AVX2 decision would be re-litigating a settled question.

Risks, trade-offs and decisions that are not engineering's

Two questions only the maintainer can answer

Both are quantified here for the first time. Neither has an engineering answer.

  1. A bypassed instance costs 101 % of an active one. The cause is the documented Issue-2 contract that Measure and Predict keep running while bypassed. Is a live Measure readout while the plug-in is bypassed worth a bypassed instance costing a full one in a large session? Changing it is a live-contract change and belongs in the same consolidated Architecture Review as W3-7.
  2. 59.3 % of the transparent idle floor is metering and loudness analysis, running regardless of Level Match being off and regardless of whether an editor exists. W3-7 and W3-8 rejected gating these for good reasons — a live Measure readout, and peaks that persist while the editor is closed — and those reasons stand. What was missing was the price. The roadmap already names the queue position: “one consolidated Review if idle-CPU ever matters commercially.” This round supplies the number that makes that call decidable.

Prior dispositions this round re-confirms

Checked against the code and left alone. None is reopened.

  • W3-7 / W3-8 — the contracts they protect are still in the code.
  • W3-9 (freeze the Velvet presence env while parked) — still load-bearing; A7-1 deliberately touches neither the env/gate nor the history writes.
  • W3-10 (Width==1 identity gate) — still Class B: 15.5 % of samples differ by ~1 ULP.
  • W3-12 residue (bypass read-back segmentation) — the read/write overlap hazard is unchanged.
  • W5-4 / W5-8 — thread-model and change-tracking hazards unchanged.
  • W5-D — the SSE2 ceiling is unchanged; nothing found here lowers it.
  • All Wave-6 GPU rejects — this round measured the software renderer only and produces no evidence that reopens any of them.
  • LookAndFeel per-paint locals — still gesture-transient; the paint profile confirms Anamorph's own drawing code is a rounding error next to JUCE's rasterizer.

W5-A is filed as “revisit only on evidence of real small-buffer host pain.” This round produces small-buffer evidence — but it points at VelvetNoise, not at the mix ring. W5-A stays deferred on its own terms.

Limits of this round

  • No wall-clock datum. Shared container; every nanosecond figure is indicative and none may be promoted into PERFORMANCE_BUDGET.md.
  • The GUI tick path was not measured — only paint.
  • Software renderer only. No GPU, no macOS or Windows rasterizer.
  • A7-1's Class-A evidence was this round's, from a scratch build — discharged in v0.9.5: regenerated on the product tree with the committed AnamorphDspDump twin diff plus a 180-configuration sweep.
  • One scenario shape. The working reference is bench.cpp's; a user on Chorus with multiband off has a different profile.

Future optimization checklist

What this round would have caught earlier, written as the questions to ask next time.

  • Measure in the configuration users run, not the default. The default has every algorithm at identity, which switches off exactly the gated fast paths that carry the cost. This round's central finding is a direct consequence of that mistake.
  • Separate the per-block term from the per-sample term. Two block sizes and a two-unknown solve is all it takes, and it exposes fixed costs that a single block size hides in the average.
  • Check every optimization that amortizes over block length at the smallest block. A fast path that wins at 128 samples can lose at 32.
  • Check every cost that scales with sample rate at 192 kHz. Anything sized from sr — delay lines, decorrelation windows, history images — is four times larger there than at the rate it was designed against.
  • Subtract startup before quoting a share. Run the same scenario at two durations and difference them; dynamic-linker and prepare() cost otherwise inflates the idle profile by several percent.
  • Prove bit-exactness by hashing output, not by argument. A hash over every sample across the scenario × block × rate cross-product costs minutes and converts a Class-A claim from an assertion into a measurement.
  • Read the disposition table before proposing anything. Four of this round's eight candidates were already settled. Re-litigating them wastes the one reviewer who can decide.
  • Price the contracts you cannot change. A rejected optimization still deserves a number — without one, nobody can tell whether the contract is cheap or is the whole idle floor.
