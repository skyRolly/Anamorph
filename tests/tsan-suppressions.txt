# ThreadSanitizer suppressions for AnamorphStateTests.
#
# ONE entry, and it is the DEADLOCK detector only. Data races are NOT suppressed
# here and must never be: `tests/tsan_canary.cpp` still fails with a data-race
# report under this file, which is what the `tsan` job's canary step proves on
# every run.
#
# WHAT IT SUPPRESSES, and why that is not hiding a defect.
#
# `juce::AudioProcessorParameter::sendValueChangedMessageToListeners` holds the
# parameter's OWN `listenerLock` while it calls listeners
# (juce_audio_processors_headless/processors/juce_AudioProcessorParameter.cpp:111-121),
# and `beginChangeGesture` does the same for the gesture dispatch (:82). So a
# listener that writes a DIFFERENT parameter from inside a dispatch nests two
# parameters' locks. Two legs of State test 75 nest them in OPPOSITE orders --
# leg D holds the edited split and writes a neighbour from inside the gesture
# open; leg G holds a neighbour being spread and writes the pin from inside its
# store -- which closes a cycle in TSan's lock-order graph and is reported as a
# potential deadlock. Both orders are taken by the MAIN thread, at different
# times, so the suite itself cannot deadlock.
#
# The nesting exists only because the harness's re-entrancy doubles create it.
# Anamorph's production listeners do not write parameters at all:
# `AnamorphAudioProcessor::parameterValueChanged` (src/PluginProcessor.h:374-377)
# is one relaxed `fetch_add`, `ViewGenWatcher::parameterValueChanged` (:579) the
# same, and `parameterGestureChanged` (src/PluginProcessor.cpp:969-1126) touches
# message-thread scalars, takes two relaxed loads of the same counter, and -- since
# ADR-0008's 2026-09-13 amendment -- reads every parameter's `getValue()` into two
# fixed vectors it owns. Those are atomic loads on the same thread: it still writes
# no parameter and takes no lock, which is the property this paragraph rests on.
# Deliberately, and its comment records that `--d2-stress-probe` once
# reported exactly this detector for an APVTS/listenerLock inversion, which was
# fixed by REMOVING the nesting rather than by a suppression. No production stack
# can contain the symbol named below.
#
# WHAT THAT DOES AND DOES NOT BUY, corrected 2026-09-08 after measuring it rather
# than reasoning about it. A TSan suppression is REPORT-scoped, not stack-scoped:
# if ANY frame of ANY stack in a report matches, the whole report is absorbed. So
# the accurate statement is narrower than the one this paragraph used to make:
#   * an inversion whose stacks are ALL production frames is STILL REPORTED --
#     measured with a purpose-built two-lock binary under the same clang: exit 66
#     with this entry loaded and neither stack naming it;
#   * an inversion that pairs a production edge with a harness edge IS absorbed --
#     also measured. That is a real residual, accepted here rather than claimed
#     away, and it is bounded by the fact that the harness edge exists only in the
#     harness: a mixed cycle cannot occur in a shipped build, where the double is
#     not compiled at all.
# The sentence this replaces said the entry "cannot mask that class" without the
# distinction, which is the stronger claim and the false one.
#
# It is narrow ON PURPOSE: it names the harness double, not the JUCE function.
# `deadlock:juce::AudioProcessorParameter::sendValueChangedMessageToListeners`
# would have worked too and would have switched the detector off for every
# parameter-lock inversion in the tree, including one a host really could reach.
#
# ONLY ONE ENTRY IS NEEDED, and the reason recorded here was WRONG until
# 2026-09-08. `WriteFromInsideAStore` was tried alongside it and
# `print_suppressions=1` reported `Matched 1 suppressions`, not two; that was read
# as "the second entry matches nothing". It does not follow, and the measurement
# says otherwise: with TWO entries that both match the SAME report, TSan credits
# exactly ONE -- verified on a scratch binary, where the credited entry was the
# SECOND in the file, so it is not even "the first entry wins". The second entry
# was therefore REDUNDANT (a second match on one report), not dead. The conclusion
# survives -- one entry, and the file stays minimal -- but the stated mechanism did
# not, and a rule kept for a wrong reason is one edit away from being dropped for a
# wrong reason too.
#
# An entry that matches nothing is still not free: it silently widens what a
# future report can be absorbed by, which is the same failure mode
# `scripts/check-citations.py` names for a stale re-aim declaration.
#
# THE ENTRY ALSO DEPENDS ON LEG ORDER, which nothing else records. It names the
# double reached from State test 75 leg D because leg D precedes leg H; re-aiming
# or removing leg D turns the report into an H-vs-G cycle whose stacks this
# pattern does not name. Editing those legs means re-checking this file, not
# assuming it still applies.
#
# The residual this does NOT close, recorded rather than suppressed away: a HOST
# that writes parameter B from inside A's dispatch on one thread while writing A
# from inside B's on another creates the same cycle for real, on locks JUCE takes
# around its own listener dispatch. Anamorph cannot close that without a
# threading-model change (ARCHITECTURE_REVIEW_GATE). See the worklog for v0.9.8.
#
# ENFORCED SINCE 2026-09-08. The rule above -- every entry must match something --
# was stated here and checked by nobody. The `tsan` job now counts the ENTRIES
# THAT MATCHED, from the per-entry breakdown `print_suppressions=1` prints, and
# requires that count to equal the number of entries in this file.
#
# It counted the SUMMARY number for one day, and that was wrong in both directions
# -- measured, not supposed: `ThreadSanitizer: Matched N suppressions` is the SUM
# OF HIT COUNTS. One entry absorbing two distinct reports prints `Matched 2` with
# ONE breakdown line (a correct file, failed), and a file with a dead entry beside
# one hit twice also prints `Matched 2` (a broken file, passed) -- which is exactly
# the mode the assertion exists to catch. The breakdown has one line per entry that
# matched at least once, so it answers the question the summary does not.
#
# One consequence worth knowing before adding an entry: two entries that both match
# the SAME report are credited as ONE, so the second reads as dead and fails this
# step. That is the intended answer -- an entry whose only matches are already
# absorbed is redundant -- but it is a surprise if you meet it cold.
#
# The two failure modes are not symmetric, which is why the assertion counts rather
# than merely requiring one match:
#   * an entry that stops matching (helper renamed, pattern drifted) is ALREADY
#     loud -- the report it was absorbing comes back and halt_on_error=1 exits 66.
#     Measured: renaming this entry gives `exit=66` with the inversion reported.
#   * an entry that matches NOTHING, because the legs that produced the report were
#     removed or restructured, is SILENT. Measured: adding a bogus second entry
#     gives `exit=0` and ONE breakdown line with two entries in the file.
# If that assertion fires, DELETE the dead entry or restore the coverage. Do not
# broaden the pattern: a wider entry is worse than none, for the reason above.
#
# SECOND ENTRY, ADDED 2026-09-14 (round 20), and it is a DIFFERENT cycle from the
# one above -- a different pair of locks, a different pair of stacks, its own
# report. It is written out here rather than folded into the paragraph above,
# because its justification is WEAKER and the difference matters.
#
# THE CYCLE. Edge one is pure production plus JUCE: restoring state takes the
# APVTS `valueTreeChanging` lock and, inside it,
# `ParameterAdapter::setNormalisedValue` -> `setValueNotifyingHost` ->
# `sendValueChangedMessageToListeners` takes a parameter's `listenerLock`
# (juce_AudioProcessorValueTreeState.cpp:413/425/457, juce_AudioProcessorParameter.cpp:113).
# Edge two is the reverse: `endChangeGesture` holds `listenerLock` while it calls
# listeners and then the `finalListener` (juce_AudioProcessorParameter.cpp:103-108),
# and State test 93's `HostSeat` -- sitting in that final seat, where a host's
# wrapper sits -- calls `pollUndoCoalesce`, which reaches `APVTS::copyState()` and
# takes the APVTS lock. Both orders are taken by the MAIN thread at different
# times, so the suite cannot deadlock.
#
# WHY THIS IS NOT THE SAME KIND OF SUPPRESSION AS THE ONE ABOVE, said plainly.
# The entry above absorbs a cycle whose second edge exists ONLY in the harness:
# no production listener writes a parameter. This one does not have that defence.
# Edge two is what a HOST does if it pumps its message loop from inside its
# gesture-end callback -- which is exactly the scenario State test 93 exists to
# reproduce, and is therefore reachable in a shipped build.
#
# ROUND 21 (2026-09-15) REWRITES THE REST OF THIS PARAGRAPH, because what it said
# is no longer true. It used to say this entry was "a placeholder for an owner
# decision, not a verdict that the cycle is benign", and that closing the cycle
# needed a threading-model change nobody had authorised. That change was
# authorised and has landed: ADR-0036 §26. The entry stays anyway, and the reason
# is a property of the DETECTOR rather than of the code.
#
# WHAT THE FIX DID. The two TIMER doors into the undo poll --
# `AnamorphAudioProcessor::timerCallback` and `pollUndoCoalesceFromTimer` -- no
# longer block on `soundReplacement`, so the message thread can no longer wait for
# a host thread's whole-sound replacement while it holds a parameter's
# `listenerLock`. Three acquisitions were reachable from those doors and all three
# are gated (the restore tail's sound re-install, `syncCommitted`'s baseline
# snapshot, and the poll body's `currentStateSet`).
#
# ROUND 22 MOVED THE FIRST OF THOSE THREE, and the paragraph above is left standing
# because what it says about BLOCKING is still exactly true. The drain's acquisition
# now spans `pendingRestore.take()` as well as the re-install it completes, in
# `adoptPendingHostState` rather than inside `adoptRestoreTail` (ADR-0036 §27): a
# timer door still only TRIES, and a failed try now consumes nothing instead of
# consuming a restore it could not finish. No door blocks that did not block before,
# and nothing here changes -- the lock is the same lock, taken by the same threads,
# in the same order.
#
# WHY THE REPORT SURVIVES IT, AND WHY THE PARAGRAPH ABOVE NAMED THE WRONG PAIR.
# Reading the actual stacks with the suppressions off, BOTH orders of this report
# are taken with `soundReplacement` already held -- and were before round 21 too:
# `copyStateWithRawValues` has taken it one line above its `copyState` since round
# 17, and `applyStatePreservingView` / `applySoundTree` take it before their
# `replaceState`. Two threads cannot hold it at once, so the APVTS-vs-listenerLock
# pair could never close. What the nested poll could actually deadlock on was
# `soundReplacement` ITSELF -- waiting for it while holding a `listenerLock` a host
# thread's `replaceState` was about to want -- and that is what round 21 fixed.
#
# TSan still reports this pair because its deadlock detector keeps a PAIRWISE
# lock-order graph and does not model an outer lock that serialises both orders.
# Measured on the fixed tree: `Matched 3 deadlock:HostSeat`.
#
# So this is a suppression of a report whose cycle cannot close, not a deferred
# decision, and not the cycle that could hang. Removing the report itself would
# mean removing the nesting -- not reading the parameter tree from inside a gesture
# dispatch at all -- which is a larger change with no defect behind it.
# `FUTURE_RISKS.md` RISK-009 carries the same correction, including the one place
# the outer-lock rule is NOT observed (`PresetManager::saveUser`, which only reads
# and so cannot join the cycle).
#
# It names the harness double, as the rule above requires -- `HostSeat` is a test
# type and cannot appear in a shipped build -- so a real host-vs-host inversion on
# these same two locks, with no harness frame in either stack, is still REPORTED.
#
# ROUND 27 (2026-09-15) DELETED THIS ENTRY, and the deletion is the evidence rather than a
# tidy-up. `deadlock:HostSeat` named State test 93's host seat, which pumps the editor's tick from
# inside `endChangeGesture`. ADR-0036 section 30 gives `pollUndoCoalesceFromTimer` a predicate --
# `anamorph::param::insideDispatch()` -- and test 93 drives its gesture through the plug-in's own
# wrapped writes, so the depth is non-zero when the pump arrives and the tick now does NOTHING:
# no drain, no poll, no flush, and so no `apvts.copyState()`. The report is gone, not absorbed.
# Measured on the round-27 tree with suppressions OFF: the whole suite raises TWO lock-order
# reports, and neither names `HostSeat`. Per the rule above -- an entry that matches nothing
# silently widens what a future report can be absorbed by -- it is deleted rather than kept
# "just in case", which also makes a regression LOUD: re-opening that door brings the report back
# with nothing left in this file to swallow it.
deadlock:WriteFromInsideAGestureOpen
#
# ROUND 24 ADDS A THIRD NAME FOR THE SAME REPORT, and it is a third name rather than
# a third finding. State test 98 (Devin R1092) drives a topology transaction with a
# host that pumps its message loop from the gesture-end callback -- the same seat
# `HostSeat` occupies, through a different harness type -- so the identical
# APVTS-vs-`listenerLock` pair is reported under a stack TSan has not seen before
# and the entries above do not match it.
#
# THE CYCLE CANNOT CLOSE HERE EITHER, AND THE REASON IS ONE LINE OF THE ROUND-21 FIX
# rather than a repeat of the argument above. `pollUndoCoalesceFromTimer` takes its
# `ScopedTryLock` on `soundReplacement` BEFORE calling the poll body and holds it
# across the whole of it -- "every acquisition inside it becomes a free recursive
# re-entry, and one try answers for all of them" -- so the M1 -> M0 order this
# report names (`listenerLock`, then `copyStateWithRawValues`' `copyState`) is taken
# with `soundReplacement` ALREADY held by that thread. The other order
# (`applyStatePreservingView` -> `replaceState` -> a store's `listenerLock`) takes
# `soundReplacement` first too. Two threads cannot hold it at once, so no pair of
# threads can occupy the two ends of the cycle. Had a host thread been holding it,
# the try would have FAILED and the poll would have returned without touching the
# APVTS lock at all -- which is exactly what ADR-0036 section 26 was for.
#
# `PumpFromGestureEnd` is a test type in `tests/state_tests.cpp` and cannot appear
# in a shipped build, so this entry obeys the same rule as the two above: a real
# host-vs-host inversion on these two locks, with no harness frame in either stack,
# is still REPORTED.
#
# ROUND 27 (2026-09-15) DELETED THIS ENTRY TOO, for the same measured reason. `PumpFromGestureEnd`
# is State test 98's seat and it calls `pollUndoCoalesceFromTimer` directly; the gesture it pumps
# from is the imager's own `addBandAt`, i.e. a dispatch this plug-in starts through
# `anamorph::param::beginChangeGesture`, so the round-27 predicate reads non-zero and the tick
# returns without touching the APVTS lock. Same measurement, same conclusion, same reason not to
# keep a dead pattern: with suppressions off the suite raises two reports and this is not one of
# them.

#             `AudioProcessorValueTreeState::copyState` takes the APVTS lock.
#   M1 => M0  `applyStateSet` -> `applyStatePreservingView` -> `replaceState` holds
#             the APVTS lock -> `valueTreeRedirected` -> `setNewState` ->
#             `setValueNotifyingHost` -> `sendValueChangedMessageToListeners`

# THIS IS NOT A NEW CYCLE. It is RISK-009's round-20 escalation verbatim -- one

# through a door round 26 added coverage for. Both orders are the MAIN thread in

# is also a host thread's `installRestoredSound` -> `applySoundTree`, which is why
# RISK-009 records it as reachable in a shipped build and refers it upward.

# WHAT ROUND 26 DID AND DID NOT CLOSE, because this entry must not be read as a
# claim that the door is safe. `flushDeferredCommands` takes `soundReplacement`

# `soundReplacement` from inside a listener's dynamic extent -- is gone. The APVTS
# edge above is NOT: `copyStateWithRawValues` still blocks on `apvts.copyState()`.
# Round 21's timer doors have exactly the same residual for exactly the same
# reason, and closing it is a threading-model change -- an ARCHITECTURE_REVIEW_GATE
# item and an owner decision, not an agent's.

# THE ENTRY IS THE HARNESS TYPE AND NOTHING ELSE, so a real host-vs-host inversion
# on these two locks, with no harness frame in either stack, is still REPORTED.
# The name was chosen to share no prefix with any other entry: the first spelling,
